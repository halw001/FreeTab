## FreeTab 性能问题源码排查（用户报告：启用插件后全系统浏览器变卡，CPU/内存正常）

- 完整遍历了全部源码（entrypoints + src + wxt.config + .output 构建产物 manifest），**未发现能解释"安装即拖垮系统"的致命缺陷**。代码已做过系统性加固（BUG 1~13 修复注释：防抖、并发锁、微任务重置标志等）。
- 构建产物 manifest（v1.1.3）确认：**无 content script、无 newtab 覆盖**，常驻代码只有 background service worker（仅监听 action.onClicked + alarms）。
- 发现的性能隐患（未改动，仅记录）：
  1. ActiveTabsSidebar.tsx:119-121 `chrome.tabs.onUpdated` 为全局监听（所有窗口），每个 dashboard 实例都会被任意 tab 变化唤醒（150ms 防抖后 query tabs）。
  2. App.tsx handleDragOver 中跨组拖拽直接 moveTab → saveState 同步 `localStorage.setItem(JSON.stringify(全量 state))`，大数据量时拖拽掉帧。
  3. useTabStore 每次变更全量双写 localStorage + chrome.storage.local，onChanged 广播到所有 dashboard 页各自全量 setState。
  4. 每个 tab 卡片挂整套 Radix Dialog+DropdownMenu，每个 group 挂 AlertDialog，收藏量大时 dashboard 首屏重。
  5. webdav/gist 后台同步 fetch 无超时控制（15 分钟一次 + 并发锁，影响有限）。
- .output 中存在 1.0.3~1.1.3 多个 zip，用户实际安装版本需确认（旧版可能不含加固修复）。
- 用户明确要求：发现问题暂不做改动。本轮未修改任何文件。

## 用户反馈 2：点击扩展图标经常 10~20 秒才打开 dashboard

- 分析 background.ts onClicked 流程，锁定最大嫌疑：**handler 在创建 tab 前先 `await chrome.tabs.query({windowId})`，且模块级 `isOpeningDashboard` 锁在 await 挂起期间会静默吞掉后续所有点击**（`if (isOpeningDashboard) return;` 无任何反馈）。query 变慢（浏览器忙/标签多/国产套壳浏览器 MV3 兼容）→ 首次点击卡住 + 疯狂点击全被吞 → 10~20s 后 query 返回 tab 才出现，与用户描述完全一致。
- 边界风险：若 query 永不 resolve，finally 不执行，锁永不释放，SW 重启前所有点击都无效。
- 次要嫌疑：dashboard 首屏重（模块加载时同步 JSON.parse 全量 localStorage；每卡片整套 Radix Dialog/DropdownMenu + StrictMode 双渲染；favicon 并发请求风暴），数据量大时白屏数秒。
- 待用户确认：点击后标签栏是"立刻出现但空白"（指向首屏渲染慢）还是"迟迟不出现"（指向点击处理卡住）。修复方案已提出（乐观先开 tab / query 加超时 / 锁限时），等用户确认后再动手。
- 用户确认：**标签页迟迟不出现**（问题在阶段一：点击处理/SW 调度），且要求**先只诊断不修改**。
- 构建产物验证：
  - 生产构建 `.output/chrome-mv3/background.js`（11KB，今天 11:56）逐字节核对，onClicked 逻辑与源码一致（await query 在前、锁静默吞点击、500ms 解锁）。
  - 开发构建 `.output/chrome-mv3-dev/`（今天 14:04 更新，background.js 83KB）含 WXT 注入的 `keepServiceWorkerAlive()`：**每 5 秒 `runtime.getPlatformInfo()` 保活，SW 永不被回收**；另有 ws://localhost:3000 HMR WebSocket（无重连循环，仅启动时连一次）、`scripting` 权限、localhost host 权限。**若用户以"加载已解压扩展"方式装的是 dev 构建，则 isOpeningDashboard 锁一旦卡死将永远无法靠 SW 重启自愈。**
- 诊断结论：tab 10~20s 不出现 = SW 冷启动慢 / onClicked 派发延迟 / tabs.query 挂起 三者之一，锁放大了"无响应"体感；环境嫌疑最大（浏览器进程繁忙或国产套壳 Chromium 的扩展 API 代理层延迟，代码注释已证实存在 360 兼容问题）。
- 已给用户无侵入定位步骤（chrome://extensions 查版本与加载路径 → SW DevTools 保活排除冷启动 → console 测 `chrome.tabs.query` 耗时 → chrome://version 报浏览器品牌）。

## 用户反馈 3（决定性线索）：SW 显示"无效"，手动输入 URL 可秒开 dashboard

- 用户暂不改动代码（未建 git 分支）。
- 现象：chrome://extensions 中 Service Worker 显示"（无效）"，点该链接没反应，点扩展图标也没反应；**但手动在地址栏输入 freedesktab.html 的完整 URL 能瞬间打开 dashboard，且 SW 随后被拉起**。
- 结论修正：dashboard 页面加载/渲染完全无问题（秒开）；`tabs.query` 也不是瓶颈。问题在 **Chrome 侧 SW 按需唤醒/onClicked 事件派发环节**——SW 闲置被杀后，点击图标 → 浏览器重启 SW → 派发事件的链条耗时 10~20s 或干脆失败。background handler 里的锁与此无关（事件根本没到 handler）。
- 候选根因排序：① 套壳/旧内核浏览器 MV3 SW 唤醒慢或事件派发延迟（代码注释显示有 360 兼容史）；② 扩展 SW 注册状态损坏（可通过停用/启用、重装修复）；③ 系统 I/O 繁忙拖慢 browser 进程（与"全局变卡"同源）。
- 待用户回报：chrome://version 浏览器品牌版本；扩展卡片"错误"按钮内容；chrome://serviceworker-internals 中该扩展 SW 的状态。
- 预备方案（待用户建分支后实施）：用 default_popup 启动页替代 onClicked——popup 页面不依赖 SW 启动，可秒开并自建 dashboard tab，从根上绕过 SW 唤醒链路；background 只保留 alarms 同步。
